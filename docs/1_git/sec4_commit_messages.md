# 커밋 메시지

> 중요도: ⭐⭐

커밋 메시지는 처음부터 잘 쓰려고 너무 긴장할 필요는 없다. 여기서는 실전에서 필요한 만큼만 아주 가볍게 본다.

## 한 줄 요약

**커밋 메시지는 이번 저장이 무엇인지 적는 짧은 메모다.**

## 어떻게 생각하면 되나?

커밋 메시지는 논문 파일 이름을 바꾸는 것이 아니라, Git 기록 옆에 붙는 짧은 설명이라고 생각하면 된다.

즉, 나중에 기록을 다시 봤을 때 "아, 이때 이런 작업을 했구나" 정도가 보이면 충분하다.

## 그냥 이렇게 쓰면 된다

처음에는 복잡하게 쓰지 않아도 된다.

- `서론 초안 작성`
- `지도교수 피드백 반영`
- `참고문헌 형식 정리`
- `오탈자 수정`

헷갈리면 에이전트에게 맡기면 된다.

- "변경 내용 보고 커밋 메시지 만들어줘"
- "적절한 메시지로 커밋해줘"
- "지금 변경에 맞는 한 줄 메시지 추천해줘"

## 이것만 기억하면 된다

1. 메시지는 짧아도 된다
2. 무엇을 했는지만 보여도 충분하다
3. 너무 멋지게 쓰려 하지 않아도 된다
4. 잘 모르겠으면 에이전트에게 맡기면 된다

## 고급 과정

초급 단계에서는 짧고 분명하게만 써도 된다. 하지만 커밋 메시지를 조금 더 신경 쓰면 Git 기록 전체의 가독성이 크게 좋아진다.

### 1. 좋은 커밋 메시지는 왜 중요한가?

커밋 메시지는 현재 작업을 설명하는 메모이면서, 나중에는 기록을 읽는 제목이 된다.

그래서 메시지가 괜찮으면:

- 예전 작업을 찾기 쉽고
- 어떤 변화가 왜 들어갔는지 추적하기 쉽고
- 여러 커밋을 훑어보기가 쉬워진다

### 2. 무엇을 써야 하나?

보통은 "이번 커밋이 하는 일"을 짧게 쓰면 된다.

예를 들어:

- `서론 문단 구조 정리`
- `GitHub 연동 안내 추가`
- `참고문헌 스타일 수정`

핵심은 파일 이름 나열보다 작업의 의미가 보이게 쓰는 것이다.

### 3. 너무 큰 커밋이 문제인 이유

커밋 하나에 너무 많은 종류의 변경이 섞이면, 메시지를 쓰기도 어려워지고 기록도 흐려진다.

그래서 좋은 메시지는 좋은 커밋 단위와 연결된다.

즉:

- 작은 의미 단위로 나누어 커밋하고
- 그 단위를 설명하는 메시지를 붙이는 방식이 가장 읽기 쉽다

### 4. 어떤 메시지는 피하는 게 좋은가?

아래 같은 메시지는 나중에 보면 정보가 부족하다.

- `수정`
- `update`
- `변경`
- `작업`

이런 표현은 너무 넓어서, 무엇이 달라졌는지 잘 보이지 않는다.

### 5. 형식은 꼭 통일해야 하나?

프로젝트마다 선호는 다르지만, 이 가이드에서는 너무 엄격한 규칙까지는 요구하지 않는다.

다만 한 프로젝트 안에서는 비슷한 톤을 유지하면 기록을 읽기 쉬워진다.
