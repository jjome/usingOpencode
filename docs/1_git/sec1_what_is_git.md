# Git이란 무엇인가

> 중요도: ⭐⭐⭐

프로그래머가 아니어도 Git을 쓸 수 있다. 여기서는 아주 가볍게만 본다.

## 한 줄 요약

**Git은 파일의 변경 이력을 기록하는 도구다.**

## 어떻게 생각하면 되나?

`thesis-example/` 폴더가 내 논문 폴더라고 생각하면 된다.

나는 그 안의 파일을 계속 고치고, Git은 그 기록을 남긴다.

## 그냥 이렇게 쓰면 된다

중간중간 "여기까지 저장"을 해두면 된다. 이것이 커밋이다.

```
[커밋 1] 아웃라인 초안 작성
[커밋 2] 서론 초안 작성
[커밋 3] 선행연구 절 추가
[커밋 4] 참고문헌 BibTeX 정리   ← 현재 상태
```

각 저장에는 짧은 메모가 붙는다.

그리고 GitHub에 올려두면:

- **백업**: 컴퓨터가 망가져도 안전하다
- **공유**: 지도교수에게 링크 하나로 공유할 수 있다
- **어디서든**: 다른 컴퓨터에서도 이어서 작업할 수 있다

## 이것만 기억하면 된다

1. 논문 폴더 하나를 정한다
2. 같은 파일을 계속 수정한다
3. 의미 있는 변화마다 커밋한다
4. 필요하면 GitHub에 백업한다

## 고급 과정

여기까지는 초급자가 Git을 일단 쓰기 위한 감각이다. 하지만 Git이 실제로 어떻게 동작하는지까지 이해하면, 실수했을 때 덜 헷갈리고 더 정확하게 다룰 수 있다.

### 1. staging은 무엇인가?

Git에는 작업 폴더와 커밋 사이에 `staging area`라는 중간 단계가 있다.

- 작업 폴더: 내가 방금 파일을 고친 상태
- staging area: 이번 커밋에 넣을 변경만 골라 담아둔 상태
- commit: 그렇게 고른 변경을 하나의 기록으로 저장한 상태

즉, Git은 그냥 바로 저장되는 구조가 아니라, **먼저 고치고 -> 커밋할 내용을 고르고 -> 그다음 기록으로 남기는 구조**다.

이 구조 덕분에 여러 파일을 한꺼번에 수정했더라도, 그중 일부만 골라서 깔끔한 단위로 커밋할 수 있다.

### 2. Git은 무엇을 저장하나?

Git은 단순히 "최신 파일 하나"만 저장하는 도구가 아니다. 파일이 어떻게 바뀌어 왔는지를 시점별로 기록한다.

예를 들어:

```
[커밋 1] 아웃라인 초안 작성
[커밋 2] 서론 초안 작성
[커밋 3] 선행연구 절 추가
```

이렇게 쌓이면, Git은 "현재 파일"만 보여주는 것이 아니라 **어떤 순서로 무엇이 바뀌었는지**를 함께 보존한다.

그래서 나중에:

- 언제 어떤 내용을 고쳤는지 확인할 수 있고
- 이전 상태와 현재 상태를 비교할 수 있고
- 필요하면 특정 시점으로 돌아가거나 일부만 가져올 수 있다

또 한 가지 중요한 점은, Git은 보통 사람들이 생각하는 것처럼 "문서 이름 뒤에 v1, v2, v3를 붙여 저장"하는 방식이 아니라, 각 시점의 상태를 추적할 수 있게 기록을 쌓아간다는 점이다.

### 3. repository는 무엇인가?

`repository`는 Git이 기록을 보관하는 저장소다. 보통은 작업 폴더 안의 `.git/` 디렉터리에 들어 있다.

- 작업 파일은 내가 직접 보는 논문 원고나 코드 파일이다
- repository는 그 파일들의 변경 이력과 커밋 정보를 보관하는 곳이다

즉, 평소에는 작업 폴더에서 글을 쓰거나 수정하고, Git은 뒤에서 repository에 그 역사를 정리해 둔다고 생각하면 된다.

### 4. 왜 Git이 편한가?

보통 파일 복사 방식으로 작업하면 `논문최종`, `논문진짜최종`, `논문최종수정` 같은 파일이 계속 늘어난다.

Git은 그 대신 **파일은 계속 같은 곳에서 작업하고, 변화의 역사만 따로 관리**한다.

즉, 문서를 여러 개 복사해 쌓는 방식이 아니라, 하나의 작업물을 시간축으로 관리하는 방식이라고 생각하면 된다.

### 5. 동작 원리를 아주 거칠게 보면

Git을 아주 단순하게 보면 다음 흐름이다.

1. 내가 파일을 수정한다
2. Git이 무엇이 바뀌었는지 감지한다
3. 그중 이번에 저장할 변경을 staging에 올린다
4. Git이 그 상태를 commit으로 남긴다
5. 나중에 필요하면 그 기록들을 비교하거나 되돌린다

초급 단계에서는 이 구조를 몰라도 쓸 수 있다. 하지만 깊게 이해하면, Git이 왜 강력한지와 왜 `staging`, `commit`, `diff`, `branch` 같은 개념이 필요한지가 자연스럽게 보인다.

그리고 더 익숙해지면, 다음 개념도 함께 이해하면 좋다.

- `HEAD`: 지금 내가 보고 있는 현재 커밋을 가리키는 이름
- `checkout` 또는 `switch`: 다른 브랜치나 상태로 이동하는 동작
- `merge`: 갈라진 작업을 다시 합치는 동작
- `remote`: GitHub 같은 바깥 저장소와 연결된 대상
