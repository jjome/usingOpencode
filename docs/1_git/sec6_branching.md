# 브랜치 기초

> 중요도: ⭐⭐

처음부터 꼭 쓸 필요는 없지만, 어느 순간부터 브랜치는 매우 편해진다. 여기서는 브랜치를 겁내지 않을 정도로만 아주 가볍게 본다.

## 한 줄 요약

**브랜치는 원본 흐름과 분리된 작업 줄기를 하나 더 만드는 것이다.**

## 어떻게 생각하면 되나?

지금 쓰고 있는 논문 본문을 바로 크게 고치기 불안할 때, 잠깐 다른 작업 줄기에서 수정해보는 것이라고 생각하면 된다.

즉, 파일을 어설프게 복사해서 여러 버전을 만드는 대신, Git 안에서 분리된 작업 흐름을 만드는 것이다.

## 그냥 이렇게 쓰면 된다

처음에는 이런 때 브랜치를 떠올리면 된다.

- 지도교수 피드백을 크게 반영할 때
- 구조를 많이 바꿔보고 싶을 때
- 다른 버전을 시험해보고 싶을 때

실제로는 에이전트에게 이렇게 맡기면 된다.

- "이번 피드백 반영은 브랜치 따서 작업해줘"
- "main은 그대로 두고 새 브랜치에서 수정해줘"
- "지금 이 작업은 브랜치를 쓰는 게 좋은지 판단해줘"

직접 할 때는 보통 이런 흐름을 본다.

```bash
git switch -c feedback-round1
git switch main
git merge feedback-round1
```

## 이것만 기억하면 된다

1. 브랜치는 다른 작업 줄기다
2. 큰 수정이나 실험성 작업에 유용하다
3. 처음에는 안 써도 된다
4. 필요할 때 에이전트와 함께 쓰면 된다

## 고급 과정

브랜치를 더 정확히 이해하면, Git이 왜 단순 복사본 관리가 아니라 구조적인 버전 관리 도구인지 보이기 시작한다.

### 1. 브랜치는 진짜 복사본인가?

느낌상으로는 복사본처럼 보이지만, Git의 브랜치는 단순 폴더 복사와는 다르다.

브랜치는 보통 "어떤 커밋을 현재 작업 기준으로 삼고 있는가"를 가리키는 이름표에 가깝다.

그래서 브랜치를 바꾼다고 해서 프로젝트 전체를 매번 새로 복사하는 방식은 아니다.

### 2. 왜 브랜치가 유용한가?

브랜치가 있으면 본 흐름을 안정적으로 두고, 다른 방향의 수정을 분리해서 실험할 수 있다.

예를 들어:

- `main`: 현재 기준이 되는 안정 버전
- `feedback-round1`: 피드백 반영 작업
- `english-version`: 다른 버전 실험

이렇게 나누면 작업 목적이 섞이지 않는다.

### 3. `switch`와 `merge`는 무엇을 하나?

- `switch`: 지금 어느 브랜치에서 작업할지 바꾸는 동작
- `merge`: 다른 브랜치의 작업 결과를 현재 브랜치로 합치는 동작

즉, 브랜치를 나누는 것만큼 다시 합치는 흐름도 중요하다.

### 4. `checkout`은 무엇인가?

예전에는 브랜치를 옮기거나 새 브랜치를 만들 때 `git checkout`을 많이 썼다.

예를 들어:

```bash
git checkout -b feedback-round1
git checkout main
```

요즘은 브랜치 이동만 놓고 보면 `git switch`가 더 읽기 쉬워서 자주 권장된다.

즉:

- `checkout`: 예전부터 널리 쓰이던 다목적 명령
- `switch`: 브랜치 이동에 초점을 맞춘 더 분명한 명령

### 5. `merge`는 실제로 무엇을 하나?

`merge`는 한 브랜치에서 만든 작업 결과를 다른 브랜치에 합치는 동작이다.

예를 들어 `feedback-round1`에서 수정한 내용을 마지막에 `main`으로 가져오는 식이다.

```bash
git switch main
git merge feedback-round1
```

즉, 브랜치는 나누는 것만 중요한 것이 아니라, 작업이 끝난 뒤 어떤 시점에 어떻게 합칠지도 함께 생각해야 한다.

### 6. `rebase`는 무엇인가?

`rebase`는 지금 브랜치의 작업을 다른 기준점 위에 다시 이어 붙이는 방식이다.

느낌상으로는 "갈라져서 작업한 내용을, 더 최신 기준 위에 다시 정리해서 올려놓는 것"에 가깝다.

그래서 `merge`와 비교하면:

- `merge`: 두 줄기의 흐름을 합친다
- `rebase`: 한 줄기의 기준점을 다시 옮겨 기록을 더 곧게 정리한다

초급 단계에서는 `merge`만 알아도 충분하다. `rebase`는 기록을 더 깔끔하게 유지하고 싶을 때 쓰는 고급 방식이라고 생각하면 된다.

### 7. 충돌은 왜 생기나?

브랜치가 갈라진 뒤 같은 부분을 서로 다르게 고치면 합칠 때 충돌이 생길 수 있다.

이것은 Git이 망가진 것이 아니라, 어느 변경을 기준으로 둘지 사람이 판단해야 하는 상황이라고 보면 된다.

이 충돌은 `merge` 때도 생길 수 있고, `rebase` 때도 생길 수 있다.

### 8. 모든 작업에 브랜치가 필요한가?

그렇지는 않다. 짧고 단순한 개인 작업은 한 브랜치로도 충분하다.

하지만 수정 단위가 커지거나, 실험성 작업이 생기거나, 협업이 들어가면 브랜치의 가치가 커진다.
